How Rodauth Interacts with Roda

The Plugin Hook

Rodauth is a Roda plugin. Loading it is one line:

  plugin :rodauth do
# configuration...
  end

Under the hood, Roda::RodaPlugins.register_plugin(:rodauth, Rodauth) makes Roda recognize the :rodauth plugin name. Roda then calls Rodauth.configure and mixes in three modules:

Module What it adds
ClassMethods .rodauth, .precompile_rodauth_templates
InstanceMethods #rodauth — access the auth instance
RequestMethods #rodauth inside route blocks (dispatcher)

The Route Dispatch Flow

  1. Browser request
  2. Roda#route block
  3. r.rodauth — calls Rodauth::RequestMethods#rodauth
  4. Rodauth::Auth#route!
  5. Looks up path in route_hash (O(1) lookup)
  6. Finds handle_<feature>_route method
  7. request.is("/login") do — Roda's path matcher
  request.is("/login") do
  check_csrf               # CSRF protection
  _around_rodauth do       # wraps hooks
    before_rodauth         # global before hook
    send(_handle_login)    # the actual GET/POST handler
  end
end

Key insight: route_hash is a frozen Hash mapping URL paths (e.g., "/login") to handler methods (e.g., :handle_login). It’s built once during post_configure, so dispatch is a simple hash lookup.

Automatic Dependencies

When plugin :rodauth loads, it automatically requires Roda plugins you likely need:

  • :json + :json_parser — if JSON API is enabled
  • :render — for templates (can be disabled)
  • :route_csrf or :csrf — CSRF protection
  • :flash — flash messages
  • :h — HTML escaping helper

The Configuration DSL

  plugin :rodauth do
# 1. Set up features (order doesn't matter — deps auto-load)
  enable :login, :logout, :reset_password, :otp

# 2. Configure database
  db DB
  accounts_table :users
  password_hash_column :ph

# 3. Set redirects
  login_redirect { '/home' }
  logout_redirect { '/goodbye' }

# 4. Set params
  login_param :email
  password_param :pass

# 5. Customize behavior with blocks
  already_logged_in { redirect '/' }
  set_session_value { |k,v| session[k] = v }  # custom session store

# 6. Override any auth method
  login_view do
    view('login', 'Sign In')  # custom title
  end
end

The three method categories:

Category What they are Example
auth_value_methods Configuration values (setters/getters) login_redirect, db
auth_methods Public runtime methods login, logged_in?
auth_private_methods Private runtime methods _set_password

All three can be overridden in the configuration block.

Feature Dependencies

Features declare dependencies with depends:

  # otp.rb
depends :two_factor_base, :require_domain, :require_hmac_secret

When you enable :otp, Rodauth automatically loads :two_factor_base first, then :otp. You never need to manually list dependencies.

The Auth Instance Lifecycle

  1. Request comes in
  2. Roda scope#rodauth(name=nil)
  • If name is nil: @_rodauth ||= Auth.new(scope)
  • If name is provided: (@_rodauths ||= {})[name] ||= Auth.new(scope)

The Auth instance holds:

  • @scope (the Roda instance)
  • @features (included modules)
  • @routes (flat list of all routes)
  • @route_hash (path to method mapping)

Methods called on the auth instance:

  • r.rodauth → route! → dispatches to feature handler
  • auth.logged_in? → checks session
  • auth.login('password') → creates session

Session Architecture

Session (server-side) Cookies (client-side)
  • account_id → 42
  • authenticated_by → ['pw']
  • two_factor_setup → true
  • otp_auth → true
  • rack.session → encrypted
  • remember → "42_hmac_key"
  • Login — sets account_id in session
  • 2FA — appends to authenticated_by array
  • Logout — clear_session
  • Remember — sets a signed cookie, auto-login on next visit

Customizing Rodauth Views

Template Resolution Priority

  1. Roda render plugin — looks in your views/ directory (e.g., views/login.str)
  2. Rodauth built-in templates — fallback to templates/login.str

To override a template: create a file with the same name in your Roda views directory.

Template Composition Pattern

Templates are composable — they call sub-templates via the rodauth local:

  <!-- templates/login.str -->
#{rodauth.login_form_header}
#{rodauth.render('login-form')}
#{rodauth.login_form_footer}

<!-- templates/login-form.str -->
<form method="post" class="rodauth" role="form">
#{rodauth.csrf_tag}
#{rodauth.render('login-field')}
#{rodauth.render('password-field')}
#{rodauth.button(rodauth.login_button)}
</form>

<!-- templates/login-field.str -->
<div class="form-group">
#{rodauth.render('login-field-label')}
#{rodauth.render('login-field-input')}
</div>

This means you can override just the input field without touching the form.

Method 1: Override Template Files

  # In your Roda app setup
plugin :render, views: 'app/views', engine: 'str'

# Then create:
#   app/views/login.str          ← overrides login page
#   app/views/password-field.str ← overrides password input
#   app/views/button.str         ← overrides ALL buttons

Method 2: Override View Methods in Config

  plugin :rodauth do
# Change the login page title
  login_view do
    view('login', 'Welcome Back!')
  end

# Add extra HTML to login form
  login_additional_form_tags do
    "<input type='hidden' name='source' value='web' />"
  end
end

Method 3: Override Field Rendering

  plugin :rodauth do
# Custom HTML attributes for all fields
  field_attributes do |field|
    'data-custom="value"'
  end

# Custom attributes for fields with errors
  field_error_attributes do |field|
    ' aria-invalid="true" class="error"'
  end

# Custom error message format
  formatted_field_error do |field, error|
    "<span class='error-msg'>#{error}</span>"
  end

# Suffix all labels (e.g., add a colon)
  input_field_label_suffix ':'
end

Method 4: Template Options

  plugin :rodauth do
# Pass custom locals to all templates
  template_opts locals: { app_name: 'MyApp' }

# Custom layout
  template_opts layout_opts: { path: 'app/views/layout.str' }
end

How Features Work Internally

Anatomy of a Feature

Every feature follows this pattern:

  module Rodauth
  Feature.define(:login) do
# ── Routes ──
    route do
# GET /login  → show form
# POST /login → process login
    end

# ── Views ──
    view('login', 'Login')

# ── Redirects ──
    redirect('/login') { request.referer || '/' }

# ── Auth Value Methods (configuration) ──
    auth_value_methods :login_redirect, :login_param

# ── Auth Methods (runtime) ──
    auth_methods :login, :logged_in?

# ── Auth Private Methods ──
    auth_private_methods :_login_from_session

# ── Dependencies ──
    depends :base

# ── Email ──
    email(:login_notice, 'Login Notice')

# ── Session/Flash Keys ──
    session_key :login_redirect_key, :login_redirect
    flash_key :login_flash_key, :login_notice

# ── Before/After Hooks ──
    before :login_route
    after :login

# ── Button Text ──
    button 'Login', :login_button

# ── Loaded Templates ──
    loaded_templates %w[login login-form login-field password-field button]
  end
end

The Request Lifecycle (Inside a Route)

  1. r.rodauth called
  2. Auth#route! looks up path in route_hash
  3. handle_login_route runs:
    • request.is("/login") do
      • check_csrf! (CSRF token verification)
      • _around_rodauth do
        • before_rodauth (global before hook)
        • before_login_route (feature before hook)
        • _handle_login(request) do
          • check_already_logged_in (skip if logged in)
          • r.get? → login_view (show form)
          • r.post? → _login (process credentials)
        • after_login_route (feature after hook)
        • after_rodauth (global after hook)
    • nil — Roda continues routing if no match

Login Feature Internals

POST /login

  1. Find account by login param
    • Not found → set error flash, redirect to /login
  2. Check account status
    • Unverified → redirect to /verify-account
  3. Verify password (BCrypt)
    • Invalid → increment invalid_logins, redirect to /login
  4. Call login('password'):
    1. Save redirect location (session)
    2. Run before_login hook
    3. login_session('password'):
      • session[:account_id] = account.id
      • session[:authenticated_by] = ['password']
    4. Run after_login hook
    5. Response: redirect with notice flash

Two-Factor Authentication Internals

Normal Login

session[authenticated_by] = ['password']

Check: authenticated_by.length >= 2?

Yes No
Full Access 2FA Required

GET /multifactor-auth

TOTP Code Recovery Code SMS Code
two_factor_authenticate('totp')
session[:authenticated_by] << 'totp'
Full Access (length >= 2)

Key session keys for 2FA:

Session Key Purpose
authenticated_byArray of auth methods used
two_factor_setupWhether 2FA was fully set up
two_factor_auth_failuresFailed 2FA attempt counter
otp_authWhether TOTP was verified
otp_setupWhether TOTP key was stored

Remember Me Internals

Login with "Remember Me" checked

  1. Generate remember_key (random token)
  2. Store in DB: account_remember_keys
  3. Set cookie: "account_id_hmac(signed_key)"

Next visit (not logged in)

  1. rodauth.load_memory (in route block)
  2. Parse cookie → extract account_id + key
  3. Verify HMAC signature
  4. Look up key in DB
Valid Invalid
Auto-login, delete old key, set new key Ignore cookie

Password Reset Internals

  1. GET /reset-password-request — User enters login
  2. POST /reset-password-request
    • Find account
    • Generate reset_key (random)
    • Store in DB: account_password_reset_keys
      • key: hmac_signed(reset_key)
      • deadline: now + 1 day
    • Send email with link: /reset-password?key=account_id_hmac(signed_key)
  3. GET /reset-password?key=...
    • Store key in session (security: don't expose in URL)
    • Redirect to /reset-password
  4. GET /reset-password
    • Look up key in session
    • Validate key exists in DB, not expired
    • Show new password form
  5. POST /reset-password
    • Validate key still valid
    • Check password requirements
    • Update password hash in DB
    • Delete reset key (single-use)
    • Redirect to login with success flash

Hook System

Every feature supports before and after hooks at two levels:

Level Hooks Scope
Global (from base) before_rodauth / after_rodauth Runs for ALL routes
Feature (per-route) before_login_route / after_login_route, before_login / after_login Runs for specific routes

Override in config:

  plugin :rodauth do
  before :login_route do
# runs before GET/POST /login
    audit_log_attempt(request.params)
  end

  after :login do
# runs after successful login
    update_last_login_date(account_id)
  end
end

app.rb — The Complete Minimal Example

  require 'roda'
  require 'sequel'
  require 'rodauth'

  DB = Sequel.sqlite # Use your real database in production

# ── Create the accounts table ──
  DB.create_table?(:accounts) do
    primary_key :id
    String :email, null: false, unique: true
    Integer :status_id, default: 2  # 2 = verified/unlocked
    String :ph  # password hash (BCrypt)
  end

  class App < Roda
# ── Plugins ──
    plugin :render, views: 'views', engine: 'str'
    plugin :flash
    plugin :route_csrf
    plugin :sessions, secret: ENV.fetch('SESSION_SECRET') { 'change-me' * 6 }, key: 'myapp.session'

# ── Rodauth Configuration ──
    plugin :rodauth do
# Database
      db DB
      accounts_table :accounts
      password_hash_column :ph

# Enable features
      enable :login, :logout, :create_account, :reset_password

# Redirects
      login_redirect  { '/dashboard' }
      logout_redirect { '/' }

# Params
      login_param    :email
      password_param :password

# Session keys
      session_key :account_id_key, :account_id
      session_key :authenticated_by_key, :authenticated_by

# Set page title for views
      title_instance_variable :@page_title
    end

# ── Routing ──
    route do |r|
# CSRF check for non-GET requests
      check_csrf! unless r.get?

# Auto-login via remember cookie
      rodauth.load_memory

# This dispatches all Rodauth routes (login, logout, etc.)
      r.rodauth

# Your app routes
      r.root do
# Require authentication
        rodauth.require_login
        view 'dashboard'
      end

      r.get 'dashboard' do
        rodauth.require_login
        "Welcome, #{rodauth.account[:email]}!"
      end
    end
  end

The Bare Minimum (No Views)

If you want to use Rodauth without any views (pure API/JSON):

  plugin :rodauth, json: true, csrf: false do
  db DB
  enable :login, :logout, :create_account
  login_redirect { '/' }
  logout_redirect { '/' }
end

route do |r|
  r.rodauth  # handles /login, /logout, etc. as JSON
end

With json: true, all responses are JSON:

  // POST /login — success
{ "status": "success", "redirect": "/dashboard" }

// POST /login — failure
{ "status": "error", "error": "invalid_login", "message": "Invalid login or password" }

Architecture Summary

Request flow:

Request → Roda route block → r.rodauth → Auth#route! → route_hash lookup → handle_feature_route

GET path POST path
Show form Process action
Render template Redirect + flash

Key design principles:

  1. Plugin-based — Rodauth is a Roda plugin, not a framework
  2. Feature-composed — Each feature is a mixin module, loaded on demand
  3. Route-hash dispatch — O(1) path-to-handler lookup, no regex scanning
  4. Template composition — Views are built from small partials you can override individually
  5. Hook-based extensibility — before/after hooks let you customize without overriding
  6. Convention over configuration — Sensible defaults, minimal config needed
  7. Database agnostic — Works with any Sequel-supported database
